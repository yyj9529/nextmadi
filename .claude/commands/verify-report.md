description: AI가 한 작업을 오너가 검토할 수 있는 형태로 다시 보고하게 한다 (증거 우선, 추측 금지)
---

방금 한 작업(또는 세운 계획)을 아래 규칙대로 다시 보고하라. 설명을 잘하려 하지 말고
**증거를 보여라.** 내가 이해 못 하는 이유는 대부분 설명이 부족해서가 아니라 확인된
사실과 네 추측이 섞여 있기 때문이다.

## 1. 먼저 이것부터 (본론 전에)

각 주장에 등급을 붙여라. 등급 없는 문장은 쓰지 마라.

| 등급 | 뜻 |
|---|---|
| 실행 | 실제로 돌려서 출력을 확인했다. 명령어와 출력을 첨부 |
| 코드 | 코드를 읽고 확인했다. 파일:줄 번호를 첨부 |
| 문서 | 문서에 그렇게 적혀 있다. 파일과 인용을 첨부 |
| 사람 | 사람이 판단했다. 누가, 언제, 원문 그대로 인용 |
| 추측 | 위 어디에도 해당 안 됨. 아직 확인 안 했다 |

"추측"이 하나라도 있으면 목록 맨 위에 모아서 먼저 보여라.

## 2. 변경 하나당 이 6개를 채워라

여러 개를 묶어서 설명하지 마라. 하나씩.

1. **어디** — 파일 경로와 식별자(케이스 id, 함수명, 줄 번호). "14개 문제"가 아니라 그 14개의 id 전부.
2. **전** — 바꾸기 전 상태를 **완전한 형태로**. JSON이면 객체 전체, 함수면 함수 전체. 한 줄만 잘라 오지 마라.
3. **후** — 바꾼 뒤 상태를 같은 방식으로 완전하게.
4. **왜** — 무엇이 문제였는지. 어떤 규칙·문서·사람 판단에 어긋났는지 출처와 함께.
5. **근거의 출처** — 4번의 각 조각이 어디서 왔는지. 내가 말한 것인지, 문서에 있는 것인지, 네가 추론한 것인지 구분. 네가 만든 예시나 문구는 "내가 지어낸 것"이라고 명시하라.
6. **영향 범위** — 이 변경이 다른 것에 영향을 주는가, 안 주는가. 안 준다면 왜 안 주는지 (예: 실행 시 서로 참조하지 않음).

## 3. 코드가 관련되면

- 실제 코드를 붙여라. 요약하지 마라.
- 변수·함수는 **어디서 만들어져 / 어디서 쓰이고 / 어디로 반환되는지** 줄 번호로 추적하라.
- 두 파일이 관련 있어 보이면 실제로 import 하는지 확인하고 답하라. 안 하면 "서로 모른다"고 명시.
- 내가 모를 수 있는 문법은 한 줄로 설명 (JS/자바에 비유해도 좋다).

## 4. 실행할 수 있으면 실행하라

이게 제일 중요하다. 설명 열 번보다 실행 한 번이 낫다.

- 돌릴 수 있는 것은 돌리고 실제 출력을 붙여라.
- 비용이 드는 것은 예상 비용을 먼저 말하고 승인을 받아라.
- 변경 효과를 주장하려면 **한 번에 한 가지만 바꿔서** 비교하라. 두 가지를 동시에 바꿔놓고 하나 때문이라고 말하지 마라.
- 아직 안 돌려본 것은 "실행 안 함"이라고 목록 끝에 따로 모아라.

## 5. 금지

- 같은 것을 여러 이름으로 부르기. 용어를 처음에 하나로 고정하고 끝까지 그것만 써라.
- 한 답변에 새 용어 3개 넘게 도입하기.
- "이렇게 하면 이렇게 될 겁니다"류의 미확인 예측을 사실처럼 쓰기.
- 코드/JSON을 한 줄만 잘라서 인용하기.
- 논문·문서 인용으로 시작하기. 근거는 사실을 다 보여준 뒤 맨 끝에.
- 내가 짧게 말한 것을 네가 길게 해석해서 규칙으로 만들기. 내 말은 원문 그대로 인용하고, 해석은 따로 표시하라.

## 6. 마지막에 이걸 붙여라

- **내가 결정해야 할 것**: 목록으로. 각 항목에 선택지와 네 추천.
- **네가 확신 없는 것**: 숨기지 말고 목록으로.
- **되돌리는 방법**: 이 변경이 마음에 안 들면 어떻게 원복하는지.

## 7. 내가 "이해가 안 간다"고 하면

다시 설명하지 마라. 순서를 바꿔라.

1. 용어부터 하나로 정리
2. 실행해서 실제 데이터 보여주기
3. 한 가지만 바꿔서 전후 비교
4. 그 다음에 나머지를 목록으로

설명을 더 길게 쓰거나 비유를 추가하는 것은 대부분 도움이 안 됐다.
