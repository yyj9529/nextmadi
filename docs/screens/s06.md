# S06 — Analysis Loading Modal

URL: none — modal overlay during S02 / S04 / S05a → S07 transition
Authentication: matches caller (S02 = none, S04/S05a = required)

## Purpose

Loading modal shown while text-only `POST /analysis` is in flight. Voice callers
reach this modal only after `POST /transcriptions` returns and the user
confirms/edits the transcript. Provides user feedback during the 5-10s LLM call,
exposes a cancel option, and times out at 30s with an error state.

## User Story

> As a user waiting for AI analysis,
> I want clear feedback that work is happening and the option to cancel if it takes too long,
> so that I don't feel stuck.

### Acceptance Criteria

1. **Given** the user submitted typed text or a confirmed voice transcript via S02, S04, or S05a,
   **When** the `POST /analysis` call begins,
   **Then** S06 modal appears as full-screen overlay (or large bottom sheet on smaller viewports) showing:
   - Coach illustration or animated icon
   - "✨ 분석 중..." headline
   - Sub-copy that cycles through 2-3 messages over time (e.g., "코치가 표현을 찾고 있어요" → "딱 맞는 톤을 고르는 중...")
   - No buttons until 10 seconds elapse

2. **Given** 10 seconds have elapsed and the call is still pending,
   **When** the timer fires,
   **Then** a "취소하기" button appears at the bottom of the modal. Tapping it aborts the fetch (`AbortController.abort()`) and dismisses the modal back to the originating screen with input preserved.

3. **Given** the call completes successfully within 30 seconds,
   **When** the 201 response arrives,
   **Then** modal dismisses with a brief transition animation and route to `/save/result/{analysis_request_id}` (S07).

4. **Given** the call exceeds 30 seconds without completing (AI_PIPELINE.md timeout),
   **When** the timeout fires,
   **Then** modal transitions in place to an error state showing:
   - "조금 더 기다려도 답이 오지 않았어요"
   - Sub-copy "다시 시도해주세요"
   - "다시 시도" primary button (re-submits the same request)
   - "취소" text button (returns to originator)

5. **Given** the API returns a non-timeout error (400 / 429 / 5xx),
   **When** the response arrives,
   **Then** modal transitions to error state with the appropriate copy:
   - 400: "입력을 다시 확인해주세요"
   - 429 (rate limit, S02 only): mirrors S02 rate-limited state with signup CTA
   - 5xx: same as 30s timeout copy

## UI states

| State | Render |
|-------|--------|
| Open, <10s | Animated icon + cycling sub-copy, no buttons |
| Open, 10-30s | Same + "취소하기" button |
| Success | Brief fade-out, then route transition |
| Timeout / 5xx error | Error icon + retry copy + 다시 시도 / 취소 buttons |
| Cancelled by user | Fade out, return to originator with input preserved |
| 400 validation error | Validation copy + 다시 입력 button |
| 429 rate limit (pre-signup) | Rate-limited copy + signup CTA |

## Edge cases

- **User taps device back button during modal** — same as tapping 취소 (abort + return). Avoids stuck modal.
- **Network drop during call** — fetch fails fast (well under 30s), error state shown immediately rather than waiting for timeout.
- **Retry from error state** — re-submits the same request body. New `analysis_requests` row is created if the original aborted before reaching the DB. **Idempotency-Key handling here TBD before W4**: if the original DID create a row, retry might create a second one. Mitigated by client passing the same `Idempotency-Key` header on retry per `openapi.yaml`.
- **User backgrounds the tab during the call** — fetch continues server-side. On return, modal is still in waiting state until response arrives or timeout.
