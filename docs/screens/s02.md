# S02 — Try Without Login

URL: `/try`
Authentication: none in the browser. Browser keeps `session_token` in
sessionStorage; the Next.js BFF sends it to Spring Boot as a claim inside
`X-Internal-Auth` (ADR-010).

## Purpose

The pre-signup entry point. A curious visitor from S01 can submit one Korean situation without creating an account, see a real S07 analysis result, and only then be asked to sign up at save time. This is the conversion funnel's first AI taste.

Subject to IP-based rate limit (2 analyses per IP per day) via `anonymous_analysis_usage`. After hitting the cap, the only path forward is signup.

## User Story 1

> As a curious first-time visitor,
> I want to try the AI analysis once without signing up,
> so that I can verify the product's value before creating an account.

### Acceptance Criteria

1. **Given** a fresh visitor lands on /try (typically from S01 "지금 바로 시도해보기"),
   **When** the page loads,
   **Then**:
   - A text input area appears with placeholder "예: 친구한테 서운한 마음을 정중하게 표현하고 싶어요"
   - Mic button for voice input shown next to the input area
   - Character counter "0 / 500" visible
   - "분석하기" submit button disabled (no input yet)
   - A new `session_token` (UUIDv4) is generated and persisted to sessionStorage under key `phraselog_session_token` if not already present

2. **Given** the user types Korean text,
   **When** character count is between 1 and 500,
   **Then** submit button enables. Counter updates real-time. At 450+ counter turns yellow, at exactly 500 it turns red and further typing is blocked at the input layer.

3. **Given** input is valid and the user taps "분석하기",
   **When** the submit runs,
   **Then** the browser calls the Next.js route handler with body `{ input_text }`. The BFF proxies to Spring Boot `POST /analysis` with `X-Internal-Auth` containing the anonymous `session_token` claim. On 201 success: route to `/save/result/{analysis_request_id}` (S07).

4. **Given** the user prefers voice input,
   **When** they tap the mic,
   **Then** same recording flow as S04 (tap-to-toggle, VAD, 60s max). Audio uploads to `POST /transcriptions` (multipart/form-data, STT only). The transcript is placed in the input area for confirmation; the user can edit it, then submits the final text via `POST /analysis` (JSON `{ input_text }`) — the same path as typed input. Decided 2026-06-10: two-step flow chosen over one-shot multipart so a mis-transcription never consumes an LLM analysis call or one of the user's 2 daily anonymous tries. S12 roleplay turns are the deliberate exception and stay one-shot.

## User Story 2

> As a visitor who has used up free analyses today,
> I want a clear path to keep using the product,
> so that I'm not stuck.

### Acceptance Criteria

1. **Given** the IP has 2 successful analyses today (`anonymous_analysis_usage.count >= 2`),
   **When** `POST /analysis` is called,
   **Then** server returns 429 with `error_code = "rate_limit_exceeded"`.

2. **Given** the 429 response is received,
   **When** UI renders the error state,
   **Then** the input area is replaced with:
   - Headline "오늘 무료 분석을 다 썼어요"
   - Sub-copy "회원가입하면 무제한으로 사용할 수 있어요"
   - Primary CTA "회원가입하기" → routes to `/login` (S03)
   - Secondary text-only CTA "내일 다시 시도" (no action; informational)

3. **Given** the rate limit resets at midnight local-server-time,
   **When** the user returns the next day,
   **Then** S02 loads normally and the visitor can try again. The `session_token` from sessionStorage persists across the reset (no new token generated unless cleared).

## UI states

| State | Render |
|-------|--------|
| Empty | Input area + placeholder + mic button + disabled submit |
| Typing valid | Counter "N / 500" + submit enabled |
| Approaching cap | Counter yellow at 450+ |
| At cap | Counter red, input blocked beyond 500 |
| Submitting | Submit button spinner, input read-only |
| Rate limited (429) | Replacement state with signup CTA |
| Network error | Inline toast "연결이 불안정해요. 다시 시도해주세요" + retry button |
| STT processing (voice input) | Mic area shows "변환 중..." with waveform fade |

## Edge cases

- **sessionStorage cleared between input and submit** — new `session_token` generated on next page load; previous attribution lost. Acceptable; pre-signup state is intentionally ephemeral.
- **Tab-scoped sessionStorage** — each tab gets its own `session_token`. Server-side rate limit by IP still applies, so the user can't bypass by opening multiple tabs.
- **Shared-NAT environments (office, school)** — multiple distinct users share one IP and may collectively hit the cap. Acknowledged limitation; signup is the workaround.
- **VPN / IP rotation users** — can technically bypass the cap. Not addressed in v1; if abuse becomes measurable, add CAPTCHA or device fingerprint in v1.1+.
- **`pending_save` from S07 → /login → return** — `session_token` from sessionStorage is read by the post-signup save handler so the original anonymous analysis is claimed under the new `user_id`. See `architecture.md` Auth / pending save flow.
- **User signs up mid-session before exhausting free tries** — once authenticated, BFF calls to `/analysis` carry `user_id` in `X-Internal-Auth` instead of anonymous `session_token`. `anonymous_analysis_usage.count` is unaffected (server checks `user_id` first). Cap doesn't apply post-signup.
