# S11 — Settings

URL: `/settings`
Authentication: required

## Purpose

Profile, coach, usage stats, and account lifecycle controls. Reached via the gear icon on S04 header (PPT v2.2 slide 13). Covers nickname editing, coach changes, today's usage display, logout, and 14-day delayed account deletion.

## User Story 1

> As a user wanting to manage my profile,
> I want to update my nickname and see my account info,
> so that the app reflects my identity.

### Acceptance Criteria

1. **Given** the user enters /settings,
   **When** the page loads,
   **Then** `GET /me` and `GET /usage/today` return profile + usage. Sections render top to bottom:
   - **프로필** — nickname (inline editable via pencil icon), email (read-only), join date
   - **내 코치** — current coach card with "변경" button
   - **오늘의 사용량** — 롤플레이 N/2, 표현 분석 N (무제한) — sources: `practice_sessions` today count, `analysis_requests` today count
   - **로그아웃** — primary text button
   - **계정 삭제** — destructive text button with 14-day notice

2. **Given** the user taps the nickname pencil,
   **When** edit mode activates,
   **Then** the nickname turns into a text input (max 100 chars). 저장 commits via `PATCH /me { display_name }`. 취소 reverts without API call.

## User Story 2

> As a user wanting to try a different coach,
> I want to switch coaches without losing my data,
> so that I can experiment with personality fit.

### Acceptance Criteria

1. **Given** the user taps "변경" in the coach section,
   **When** the modal opens,
   **Then** 3 coach cards appear (same comparison layout as S03b). Current coach is marked.

2. **Given** the user selects a different coach,
   **When** the confirmation runs,
   **Then** `PATCH /me { selected_coach_id }` is called. On success: modal closes, coach section updates, toast "코치가 변경됐어요".

3. **Given** the user is in an active roleplay session in another tab when coach changes,
   **When** the next roleplay starts after the change,
   **Then** the new coach is used. Existing in-progress sessions retain their original `coach_id` (committed at session start in `practice_sessions.coach_id`).

## User Story 3

> As a user wanting to leave the service,
> I want a clear deletion path with a safety window,
> so that I can undo if I change my mind.

### Acceptance Criteria

1. **Given** the user taps "계정 삭제",
   **When** the confirmation dialog appears,
   **Then** copy: "14일 동안 로그인하지 않으면 모든 데이터가 영구 삭제됩니다. 그 안에 로그인하면 복원돼요." With buttons "취소" and "계속 진행".

2. **Given** the user confirms,
   **When** `DELETE /me` is called,
   **Then** server sets `users.scheduled_deletion_at = now() + interval '14 days'`. Frontend signs the user out and routes to S01 with toast "14일 안에 다시 로그인하면 복원돼요".

3. **Given** the user signs back in within 14 days,
   **When** the NextAuth callback runs,
   **Then** server detects `scheduled_deletion_at IS NOT NULL` and calls `POST /me/cancel-deletion` (clears the field). User lands on /home normally. Toast "다시 만나서 반가워요".

4. **Given** 14 days pass without login,
   **When** the daily cleanup job runs,
   **Then** the row is hard-deleted (cascade removes all owned data per `data-model.md` FK relationships).

5. **Given** the user taps "로그아웃" (not deletion),
   **When** signout runs,
   **Then** NextAuth clears the session cookie. Route to S01.

## UI states

| State | Render |
|-------|--------|
| Loading | Section skeletons |
| Loaded | All sections rendered |
| Nickname edit mode | Inline text input + 저장 / 취소 |
| Coach change modal open | 3-coach comparison modal |
| Deletion confirm dialog | Centered with destructive copy |
| Action errors | Section-scoped toast |

## Edge cases

- **Nickname validation** — server enforces `display_name VARCHAR(100)`. Empty submitted? **TBD before W4**: allow empty (clears display name) or require minimum 1 char.
- **Coach change mid-session** — handled (see User Story 2 step 3). New session uses new coach; existing session unchanged.
- **Daily counters reset at midnight** — local-server-time boundary. UI may briefly show 0 immediately after midnight, then update on next page load. Acceptable.
- **Deletion grace window edge** — if user signs in at hour 13 of day 14, `scheduled_deletion_at` is still in the future and cancellation succeeds. If hour 1 of day 15, the cleanup job may have already run; user sees signup screen with no data. Edge timing acceptable for v1.
