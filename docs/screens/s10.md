# S10 — Review

URL: `/review`
Authentication: required

## Purpose

Active recall practice on saved expressions. Korean situation shown first; user attempts to recall English; then evaluates their recall on a 3-button scale. Next review date is scheduled automatically using a simple ×1 / ×2 / ×3 interval model (ADR-002).

SM-2 and other adaptive ease-factor algorithms are explicitly deferred to v1.1+ (PRD section 4.3, PPT v2.2 slide 12). The history table `review_attempts` accumulates from v1 onward so a future upgrade has training data.

## User Story 1

> As a user with saved expressions due for review today,
> I want to see Korean first and try to recall English on my own,
> so that I build memory through active effort rather than passive reading.

### Acceptance Criteria

1. **Given** the user enters /review,
   **When** the page loads,
   **Then** `GET /review/today?limit=10` returns up to 10 due cards plus `total_due`. Due = `next_review_at <= now()` AND `removed_from_queue_at IS NULL` AND parent expression not soft-deleted.

2. **Given** a card is rendered,
   **When** the user sees it,
   **Then** only the Korean `original_situation` is visible plus a "정답 보기 →" button. The English variant card and three evaluation buttons are hidden.

3. **Given** the user taps "정답 보기",
   **When** the reveal animation runs (~250ms),
   **Then** the English variant card (english_text + IPA + korean_pronunciation + tips) slides up. The three evaluation buttons (어려움 / 기억남 / 완벽) become visible together — never one before another.

4. **Given** the queue is empty,
   **When** the page loads with `total_due = 0`,
   **Then** empty state shows "오늘 복습할 카드가 없어요" with CTA to /library.

## User Story 2

> As a user who just attempted recall,
> I want to rate how well I remembered and have the next review scheduled automatically,
> so that difficult cards return sooner and easy cards space out.

### Acceptance Criteria

1. **Given** the English is visible and the user taps **어려움**,
   **When** submit runs,
   **Then** `POST /review/{review_card_id}/submit` with `rating="hard"` is called. Server: `next_interval_days = 1`. Writes one `review_attempts` row and updates `review_cards`.

2. **Given** the user taps **기억남**,
   **When** submit runs,
   **Then** server: `next_interval_days = previous_interval_days × 2`.

3. **Given** the user taps **완벽**,
   **When** submit runs,
   **Then** server: `next_interval_days = previous_interval_days × 3`.

4. **Given** any rating is submitted,
   **When** toast appears,
   **Then** message format:
   - hard: "📅 내일 다시 만나요"
   - good: "📅 {N}일 후 다시"
   - easy: "🎉 {N}일 후 다시!"

5. **Given** the rating is submitted,
   **When** the card advances,
   **Then** the next card from the loaded array is shown. After the last loaded card, `GET /review/today?limit=10&exclude_ids=...` fetches the next batch.

6. **Given** all due cards are reviewed,
   **When** the user submits the last one,
   **Then** completion state shows: count summary ("오늘 8개 복습 완료"), bookshelf count animation, "홈으로" CTA.

## User Story 3

> As a user mid-session,
> I want to leave without losing progress,
> so that I can return later without re-doing reviewed cards.

### Acceptance Criteria

1. **Given** the user taps the X close button mid-session,
   **When** confirmation modal appears,
   **Then** options: "계속하기" (dismiss modal), "나가기" (route to /home).

2. **Given** the user chose "나가기",
   **When** the route runs,
   **Then** already-submitted ratings remain committed (server-side update happened at each tap). Unreviewed cards remain in the queue for the next session.

3. **Given** a card was shown but not rated (user backed out before tapping a rating button),
   **When** the user re-enters /review,
   **Then** that card appears again because its `next_review_at` and `last_reviewed_at` were not modified.

## UI states

| State | Render |
|-------|--------|
| Loading first batch | Card skeleton with shimmer |
| Active | Progress indicator "N / Total" + progress bar + current card |
| Answer hidden | Korean visible, "정답 보기" button, evaluation buttons hidden |
| Answer revealed | English card slid up, 3 evaluation buttons visible |
| Submitting | Buttons briefly disabled during API call |
| Empty queue | Empty state, CTA to /library |
| Completed | Summary screen, CTA to /home |
| Network error on submit | Card does not advance, retry CTA, no state change committed |

## Edge cases

- **`current_interval_days` initial value** — decided 2026-06-10 (PRD Open Question 5, data-model.md Open Question 1): a newly saved card gets `next_review_at = now()` and `current_interval_days = 1`. The card is due immediately, while the interval base stays 1 so the multiplication rules work (`good`: 1 x 2 = 2, `easy`: 1 x 3 = 3). Storing interval 0 was rejected because 0 x 2 = 0 would trap cards in a permanently-due state.
- **Cards loaded but expression soft-deleted in another tab** — server-side filter `e.deleted_at IS NULL` excludes these from the next batch. Client treats as if card was never there.
- **User completes 10 cards and the next batch returns 0** — completion state shown, not "empty queue" state. Different messaging.
- **`removed_from_queue_at` set via S09 mid-review** — same as soft-delete case; client does not see the removed card on next batch fetch.
- **Exactly 1 card due** — works the same as N cards; completion state on submission. No special-case UI needed.
