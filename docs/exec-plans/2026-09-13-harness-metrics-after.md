# 하니스 개선 후 재측정 (after 스냅샷)

- 측정일: 2026-09-13 (KST)
- before: `docs/exec-plans/2026-08-27-harness-baseline.md` (commit `638738d`)
- after: commit `bd8c746` (origin/main)
- 측정 도구: `scripts/harness-metrics.sh`. before와 **같은 스크립트를 수정 없이** 재실행했다
- 재현: 커밋마다 워크트리를 따로 만들고 `bash scripts/harness-metrics.sh`를 실행

## 결론

**이 스크립트의 지표로는 하니스 개선 효과를 확인할 수 없다.**

- 컨텍스트 비용은 실제로 10% 늘었다. 줄이려던 방향과 반대다. 늘어난 분량은 대부분 실수 대장 운영 규칙이다
- 리뷰 재작업률과 세션 마찰률은 숫자상 크게 나빠졌다. 그러나 확인해 보니 **측정 도구가 무너진 것**이다. 개선 자체가 키워드 적중률을 끌어올렸다
- 도구가 유효하게 잰 항목(깨진 링크, ADR 인덱스, TBD 수, 열린 이슈)은 유지되거나 조금 나아졌다

즉 "좋아졌다"도 "나빠졌다"도 이 데이터로는 말할 수 없다. 이 기록의 가치는 거기에 있다. 키워드로 센 대리 지표는 **기록 습관을 바꾸는 개입을 평가할 수 없다.**

## 0. 먼저 확인한 것: 도구가 같은 방식으로 재는가

before 커밋(`638738d`)에서 스크립트를 이 컴퓨터로 다시 돌렸다. 섹션 1~3의 수치가 before 기록과 **정확히 일치**했다 (항상 로드 36,670바이트, 티켓 로드 57,622바이트, docs 86개 / 625,554바이트, TBD 34, exec-plan 25, 리뷰 18, 깨진 링크 0). 줄바꿈 설정이 다른 환경에서도 같은 값을 내므로 before/after 비교가 성립한다.

재현되지 않은 항목이 하나 있다. before 기록의 "permission allow 규칙 6"은 커밋된 `.claude/settings.json`에서 나오지 않는다(두 시점 모두 0). 당시 커밋되지 않은 로컬 설정을 쟀던 것으로 보인다. 또 스크립트의 `grep -c ... || echo 0`이 0일 때 `0`을 두 번 출력한다. 이 행은 비교에서 뺐다. 도구를 같게 유지하려고 스크립트는 고치지 않았다.

**측정 시점 주의:** before 기록은 08-27에 쟀지만 측정한 브랜치가 08-03의 main에서 갈라져 있었다. 그래서 08-25에 main에 들어간 #136(로딩 정책 단일화), #137(실수 대장), #138(`/ticket-start` 간소화)이 before에 **포함되지 않았다.** 이번 비교는 "8월 초 하니스 대 9월 중순 하니스"다.

## 2. 리뷰 재작업률 — 숫자는 나빠졌지만 판단할 수 없다

| 집계 방식 | before (≤08-26, 18건) | after (≥08-27, 5건) |
|---|---:|---:|
| 스크립트 원래 방식 (키워드 적중) | 10건, 55% | 4건, 80% |

스크립트 누적값(전체 23건): 14건, 60%.

**키워드 적중이 실제 재작업을 뜻하지 않았다.** 키워드 중 실제로 걸린 단어는 전부 "blocker" 하나였고, before 적중 10건 중 5건은 "blocker 없음", "not a blocker", `## Blockers` 아래 "None."처럼 **없다는 말**이었다. 그래서 리뷰를 한 건씩 읽고 blocker를 실제로 찾은 경우만 다시 셌다.

보정해도 after가 높지만 **판단할 수 없다.**

- after 표본이 5건이다
- after 5건 중 2건(#36)은 **before 시점 하니스로 08-04에 작성된 코드**를 리뷰한 것이다
- 08-30 이후 `docs/reviews/`에 새 리뷰 파일이 **0건**이다. 리뷰 기록 방식이 바뀌어 이 지표는 사실상 수집이 멈췄다

## 3. 세션 마찰 — 개선이 측정 도구를 오염시켰다

| 집계 방식 | before (≤08-26, 103건) | after (≥08-27, 28건) |
|---|---:|---:|
| 하니스/문서 마찰 키워드 | 44% | 78% |
| 에러/실패 키워드 | 87% | 96% |

스크립트 누적값(전체 132건): 마찰 51%, 에러 89%, 정비 13%. before 기록의 104건 = 날짜 있는 103건 + 날짜 없는 1건이고, 마찰 적중 46건이 두 기준에서 같다.

**마찰이 늘었다고 해석하면 안 되는 근거:**

| 검사 | before | after |
|---|---:|---:|
| 실수 대장 / 재발 언급 (`docs/solutions`, 재발, 실수 대장) | 9% | **78%** |
| dev-log 평균 길이 | 3,232바이트 | **7,861바이트 (2.4배)** |
| 중복 | 11% | 35% |
| 불일치 / drift | 17% | 42% |
| 충돌 | 18% | 35% |
| 롤백 | 8% | 7% |

#137 실수 대장은 세션마다 실수를 dev-log에 서술하고 재발 이력을 적도록 **요구한다.** 그 결과 dev-log가 2.4배 길어졌고, 긴 문서일수록 "중복", "충돌", "불일치" 같은 단어가 들어갈 확률이 높다. 기록 규칙과 직접 관련이 적은 사고 단어인 "롤백"은 8%에서 7%로 **거의 그대로**다.

측정하려던 것(마찰)과 개선한 것(마찰을 기록하는 습관)이 같은 단어를 공유해서, 기록이 좋아질수록 마찰이 늘어난 것처럼 보인다.

## 다음에 잰다면

키워드 대리 지표는 기록 습관이 바뀌는 개입 앞에서 쓸 수 없다는 게 이번에 확인됐다. 다음 비교에서는 기록 방식의 영향을 받지 않는, **이미 구조화된 데이터**를 쓰는 편이 낫다. 후보만 적고 구체적 설계는 그때 정한다.

- `docs/solutions/*.md`의 `## 재발 이력` 목록 길이 — 한 줄에 한 건이라는 형식이 정해져 있다
- PR 단위 데이터(`gh`) — 머지 전 추가 커밋 수, 리뷰 코멘트 수

before 기록의 원칙("손으로 두 번 세면 비교가 성립하지 않는다")은 그대로 유효하다. 이번에 추가된 교훈은 **같은 도구로 재도 측정 대상이 도구를 바꾸면 비교가 성립하지 않는다**는 점이다.
