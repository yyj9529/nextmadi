# 문서에 적힌 관찰·숫자를 현재 사실로 씀

## 증상

- #131 본문에 "`localhost`는 연결 안 되니 `127.0.0.1`로 열라"고 적혀 있었다. 그 한 줄이
  버그를 유발하는 유일한 주소로 모두를 안내해 repro가 몇 주 늦어졌다 (`20260829_0555`)
- S07 평가 규모를 오너에게 "케이스 22개, 1회 약 $1.17"이라고 설명했다. 22는 PR #160
  본문과 2026-09-03 exec-plan에서, $1.17은 6월 기록에서 가져온 숫자였다. 실제는
  `test_cases.json` 82개 + `behavior_contract.json` 8개 = 90개이고, 2026-09-09 전체
  실행은 $16.52였다. 오너가 지적해서 알았다 (`20260922_0625`)

## 근본 원인

이슈 본문, PR 설명, 지난 exec-plan은 **그때의 관찰**이다. 저장소의 현재 상태가 아니다.
그런데 둘 다 같은 저장소 안에 텍스트로 있어서, 읽을 때 구분되지 않는다.

숫자와 증상 서술은 특히 위험하다. 코드가 바뀌어도 그 문장은 따라 바뀌지 않기 때문에
시간이 지날수록 틀릴 확률만 올라간다. 그런데 문장 자체는 구체적이고 확신에 차 있어서,
읽는 쪽은 오히려 더 믿는다.

## 올바른 방법

- 숫자를 말하기 전에 **그 숫자가 사는 파일**을 연다. 케이스 수는 `test_cases.json`,
  비용은 실행 아티팩트나 dev-log, 버전은 lock 파일이다. 이슈 본문은 출처가 아니다
- 이슈·PR 본문에서 가져온 사실은 출처와 시점을 함께 말한다.
  "#160 본문 기준(2026-09-13)"처럼 쓰면 듣는 쪽이 낡았을 가능성을 판단할 수 있다
- 이슈를 **쓸 때도** 관찰과 사실을 나눠 적는다. "`localhost`에서 실패함(관찰, 원인 미확인)"과
  "`localhost`는 연결 불가(사실)"는 독자를 전혀 다른 곳으로 보낸다
- 오래된 계획 문서의 수치는 인용하지 말고 갱신하거나 지운다. `CLAUDE.md`의 TBD 규칙과
  같은 이유다 — 낡은 숫자가 남아 있으면 문서 전체의 신뢰가 깎인다

## 자동화 후보

재발 2회. 규칙상 아직 노트 단계이고 자동 차단은 3회부터다. 3회가 되면 아래를 검토한다.

- 저장소 사실을 세는 숫자(케이스 수, 테스트 수, 비용)는 문서에 직접 쓰지 않고 생성한다.
  README의 테스트 수를 XML 리포트에서 뽑아 쓴 선례가 있다
- 평가 규모·비용을 말해야 하는 문서는 최신 실행 아티팩트 파일명을 함께 적게 하고,
  그 파일이 없으면 CI에서 경고
