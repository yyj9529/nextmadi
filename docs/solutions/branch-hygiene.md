# git 브랜치 위생 사고

## 증상

- 한 브랜치에 3개 티켓 변경이 **커밋 0개**인 채 작업 트리에만 존재 (`20260718_0625`)
- rebase 후 detached HEAD 상태로 방치
- 티켓과 무관한 편집(`.vscode/`, `package-lock.json`, 다른 티켓 CSS)이 섞여 리뷰 불가
- squash-merge 저장소에서 브랜치 삭제 판단을 커밋 카운트로 하다가, 로컬 브랜치명과
  병합된 PR head 브랜치명이 달라 혼선 (`20260722_0053`)
- 수정한 버그가 브랜치 사고로 유실되어 같은 버그가 다시 나타남 (`20260718_0945`)
- 세션 도중 브랜치가 바뀐 것을 모르고 `main`에 직접 커밋 (`20260826_0447`)
- 세션 도중 브랜치가 바뀐 것을 모르고 **다른 티켓의 feature 브랜치**에 커밋
  (`20260910_0903`). main이 아니었으므로 main 차단 훅으로는 잡히지 않는다
- `git checkout main && git pull`에서 pull만 실패. 체크아웃은 이미 끝나 stale main 위에
  앉았고, 방금 머지한 내용이 워킹트리에서 사라진 것처럼 보였다 (`20260829_1500`)
- PR이 **머지 완료(보라색)인데 코드가 main에 없다.** base가 `main`이 아니라 다른 작업
  브랜치였고, 그 브랜치를 main으로 넣는 PR이 **51초 먼저** 머지돼 실어 나를 배가 이미
  떠난 뒤였다. PR 목록은 전부 merged라 눈으로는 아무 이상이 없다 (`20260902_2226`, #156/#24)

## 근본 원인

**커밋되지 않은 작업은 git이 존재를 모른다.** 커밋된 것은 `git reflog`로 살릴 수
있지만 한 번도 커밋 안 된 변경은 복구 수단이 없다. `git checkout .` 한 번이면 증발한다.

뿌리는 하나다: 티켓 하나를 끝낼 때까지 커밋하지 않고 작업 트리에 쌓는 습관.
거기서 파생되어 무관 변경 혼입, 롤백 커플링, blame 오염이 전부 따라온다.

## 올바른 방법

- **티켓당 브랜치 하나.** 편집 전에 브랜치부터 만든다
- **자주 작게 커밋.** 작업 트리에 하루치 이상 쌓지 않는다
- 다른 티켓이 생각나면 그 브랜치로 옮겨서 한다. 지금 브랜치에 얹지 않는다
- 위험한 정리(rebase, 커밋 재구성, 파일 분리) 전에는 **항상 WIP 스냅샷 먼저**.
  단 `git stash create`는 untracked를 포함하지 않으므로 별도 처리 필요
- 브랜치 삭제 판단은 커밋 카운트가 아니라 "내용이 main에 실제로 있는가"를
  파일/클래스 단위로 확인
- **PR을 열 때 base가 `main`인지 본다.** 다른 티켓 브랜치 위에서 브랜치를 따면 GitHub이
  base를 그 브랜치로 잡아준다. 그 상태로 머지하면 코드는 중간 브랜치에 얹히고, 그
  중간 브랜치가 이미 main에 들어간 뒤라면 main으로 갈 경로가 사라진다. 머지 버튼은
  "main으로 보내기"가 아니라 "이 PR이 적어둔 목적지로 보내기"다
- **"PR 다 머지함"은 "코드 다 들어감"이 아니다.** 티켓을 닫기 전에 main에서 파일 존재를
  확인한다 — `git ls-tree -r --name-only origin/main | grep <새로 만든 파일>`.
  `gh pr list --state merged --json number,title,baseRefName`로 목적지도 함께 본다
- PR 올리기 직전 `git fetch && rebase origin/main` — 충돌을 리뷰 중에 만나지 않는다
- **커밋 직전에 `git branch --show-current`를 확인한다.** 세션이 길어지면 그 사이
  오너나 다른 세션이 브랜치를 바꿔놓을 수 있다. 세션 시작 때 확인한 브랜치가 커밋
  시점에도 같다고 가정하지 않는다
- **`checkout && pull`은 두 동작이다. pull이 실패해도 checkout은 이미 끝나 있다.**
  실패를 무시하면 stale main 위에 앉은 채로 계속 일하게 된다. 머지 직후 동기화할
  때는 `git rev-list --left-right --count main...origin/main`이 `0 0`인지 눈으로
  확인한다 — 명령이 성공했다는 인상 말고 실제 ref를 본다

## 자동화 후보

재발 11회. 3회 기준을 한참 넘겼는데 아직 사람 확인에만 의존 중이다.

11회차는 기존 후보가 **구조적으로** 못 잡는 경우였다. 아래 훅은 전부 "브랜치가
`main`이면 막는다"인데, 그때 옮겨간 곳은 main이 아니라 다른 티켓의 feature
브랜치였다. 커밋도 브랜치도 정상으로 보였고 소속만 틀렸다. 4회 이상 규칙에 따라
조치를 재설계해야 한다는 뜻이므로 후보를 하나 더 든다.

- **작업 시작 시점의 브랜치를 파일에 적어두고, 커밋 전에 대조한다.** 세션 초반에
  `git branch --show-current`를 세션 스크래치에 기록하고, `git commit` PreToolUse
  훅이 현재 브랜치와 그 값을 비교해 다르면 막는다. "main인가"가 아니라 "내가 시작한
  그 브랜치인가"를 묻는 것이 이 패턴의 정확한 질문이다

- PreToolUse(Edit/Write) 훅: 현재 브랜치가 `main`이면 편집 차단
- PreToolUse(Bash) 훅: `git commit`인데 현재 브랜치가 `main`이면 차단.
  8회차가 정확히 이 경우였고, Edit 차단만으로는 못 막는다 (편집은 브랜치에서 하고
  커밋만 main에서 하는 경우가 생긴다)
- 세션 Stop 훅 확장: 작업 트리에 커밋 안 된 변경이 N개 이상이면 경고 출력
  (기존 `check-dev-log.ps1`과 같은 자리)
- **base가 `main`이 아닌 PR은 열 때 경고한다.** `gh pr create` 앞단(훅 또는 래퍼)에서
  base를 확인하고, 의도한 스택 PR이 아니면 막는다. 10회차가 이 경우였고 위 두 훅으로는
  못 잡는다 — 브랜치도 커밋도 전부 정상이었고 목적지만 틀렸다
- CI 또는 주기 작업으로 **"merged인데 base가 main이 아니고, 그 base도 main에 없는 PR"**
  을 열거한다. 사람이 PR 목록을 눈으로 훑어서는 절대 안 보이는 상태다
