# stale .next 캐시

## 증상

- 라우트 파일이 존재하고 커밋까지 돼 있는데 `/home`, `/try`, `/library` 등
  **전 라우트가 404**. `/`만 200 — 다만 5회차(`20260916_0849`)는 `/`와 `/api/*`까지
  전부 404였다. `/`가 살아있는지는 판정 기준이 아니다
- `public/` 정적 파일(`/icon.svg` 등)은 200. 서버는 멀쩡히 떠 있다
- 라우트를 옮긴 뒤 `typecheck`가 TS2307로 실패 — 삭제된 옛 경로를 참조

## 근본 원인

Turbopack의 `.next` dev 캐시 손상. **코드 문제가 아니다.**

판정 근거가 명확했다: page 파일 전부 존재, git 트리 clean, `middleware.ts` 없음,
소스에 `notFound()` 호출 없음, `next.config.mjs`에 라우팅 영향 설정 없음, 그리고
`npx next build`는 32개 라우트를 정상 발견하고 성공. dev 전용 문제로 확정.

느린 디스크 환경에서 새 라우트를 추가한 직후에 잘 생긴다. dev 로그 첫 줄의
`⚠ Slow filesystem detected` 경고가 그 환경임을 알려준다.

5회차에서 더 빠른 판정 근거를 찾았다: `.next/dev/logs/next-development.log`에는
`○ Compiling /try ...`가 남아 컴파일은 성공했는데, 라우팅 테이블인
`.next/dev/server/app-paths-manifest.json`에는 그 라우트가 없다. 컴파일 산출물
(`.next/dev/server/app/**/page.js`)과 매니페스트가 어긋나면 캐시 손상으로 봐도 된다.
`next build`를 돌리기 전에 이 두 파일만 비교해도 몇 초 안에 판정된다.

## 올바른 방법

"파일은 있는데 404"이면 거의 항상 코드가 아니라 dev 서버 상태다. 순서:

1. `next build`가 라우트를 찾는지 확인 (찾으면 코드는 무죄, dev 전용 문제 확정)
2. dev 서버 종료 + 잔여 node 프로세스 정리
3. **`.next` 삭제 후 재기동** — 재시작만으로는 안 풀린다. 이게 핵심

2번까지 끝냈으면 3번은 `bun run dev:clean` 한 줄이다 (`.next` 삭제 + `next dev`).
서버가 살아 있으면 Windows에서 파일 잠금 때문에 삭제가 실패하니 종료가 먼저다.

코드를 고치려 들기 전에 이 4단계를 먼저 한다. 4회 모두 코드 수정 0줄로 해결됐다.

## 현재 반영

재발 5회. 발생 후 대응이라 자동 차단(hook/CI)은 어렵고, **복구 비용을 명령 하나로
줄이는 쪽**으로 갔다.

- `bun run dev:clean` — `.next` 삭제 후 dev 기동. 4회차에서 후보로만 적어두고 실제로
  넣지 않았고, 그래서 5회차에도 수동으로 종료·삭제·재기동을 했다. 5회차에
  `package.json`에 추가했다. 후보 목록은 조치가 아니다
- 관련 없는 원인과 헷갈리지 않도록: 하이드레이션만 안 되고 라우트는 200이면
  캐시가 아니라 HMR origin 문제다 (`next.config.mjs`의 `allowedDevOrigins`, #131)
