> Purpose: A one-page map to become the person who knows this project better than anyone in the world.
> Covers why every file exists, what breaks without it, and when and how to use it.

## 0. The big picture: files fall into just 6 groups

```
[0] Entry / Orientation   → What AI and humans read first every session (what this project is, how we work)
[1] Blueprints            → What to build (specs that let AI write correct code)
[2] Decision Records (ADR)→ Why we decided that way (prevents rehashing the same debates)
[3] Quality / Validation  → Numbers to judge whether what was built is actually good
[4] AI Collaboration Ops  → How agents (Claude Code / Codex) operate
[5] Learning / Meta       → Supplementary material I added while studying
```

One-sentence summary: **Blueprints (1) make AI write the right thing; validation (3) tells us whether it's actually good.**

## 2. File-by-file descriptions (role / why needed / what breaks without it)

### [0] Entry / Orientation

**Always-load = "base set"** (read automatically every session)

| File path | Role (why needed) | What breaks without it |
|---|---|---|
| `START_HERE.md` | Guides the reading order for documents | Every session, agents wander not knowing where to start |
| `PROJECT_CONTEXT.md` | Product identity, target user, reason for existence | AI mistakes this for "just an English app" and works off-target |
| `CLAUDE.md` | Working agreement (how AI should operate) | AI behavior becomes inconsistent; rules get re-explained every session |
| `AGENTS.md` | Pointer that makes Codex read CLAUDE.md | The two tools operate under different rules |
| `SECURITY.md` | Forbidden zones and approval rules | AI takes risky actions (deploy, delete) autonomously |
| `docs/decisions/INDEX.md` | One-line ADR summaries (always-loaded) | Full ADRs get read every session, wasting context |

**External-facing · not always-loaded** (not read every session)

| File path | Role | What breaks without it |
|---|---|---|
| `README.md` | External intro for first-time visitors | No first-impression material for hiring or collaboration |

### [1] Blueprints

| File path | Role (why needed) | What breaks without it |
|---|---|---|
| `docs/PRD.md` | v1 scope, 14 screens, user stories | Scope expands indefinitely |
| `docs/data-model.md` | DB tables, indexes, relationships | AI generates a different schema each time → conflicts |
| `docs/AI_PIPELINE.md` | STT→LLM→TTS, JSON schemas, cost, routing | AI features diverge; cost uncontrollable |
| `docs/architecture.md` | Server, deploy, observability structure | Operational incidents; deploy steps unclear |
| `docs/api/openapi.yaml` | Front ↔ back API contract | Both sides assume different formats → bugs |
| `docs/DESIGN.md` | UI style and design tokens | Each screen has its own design; consistency collapses |
| `docs/PhraseLog_screen_query_crud_explained_v2.md` | Per-screen read/write table mapping | Screen-to-DB connections get guessed each time → omissions |
| `docs/screens/sNN.md` (14 files) | Per-screen G-W-T, UI states, edge cases | "Build this screen" is too vague; results are unstable |

### [3] Quality / Validation

| File path | Role (why needed) | What breaks without it |
|---|---|---|
| `docs/EVAL_PLAN.md` | Evaluation strategy and tiers | "Did the prompt improve?" is judged by feel |

## 3. Usage examples — situation / files / reason / prompt

Notation: **base set** = group [0] (`START_HERE` + `CLAUDE.md` + `PROJECT_CONTEXT` + `SECURITY` + `docs/decisions/INDEX.md`).
Always read first at session entry. The prompts below add task-specific files on top of that.
Role separation (harness): typically **one agent implements → a different agent reviews**.

---

### Example 1) Login feature — Claude Code

**Files:** base set + `docs/screens/s03.md` + `docs/api/openapi.yaml` (auth) + `docs/data-model.md` (users)
**Reason:** Screen behavior, API contract, and DB structure all need to align for login to work.

```
Read the session entry docs first (START_HERE → CLAUDE.md → PROJECT_CONTEXT → SECURITY → docs/decisions/INDEX.md).
Then implement the login feature using the User Story and G-W-T from docs/screens/s03.md,
the auth endpoints from docs/api/openapi.yaml, and the users table from docs/data-model.md.
Before implementing, write a plan to docs/exec-plans/ using the docs/exec-plan-template.md format.
All G-W-T in s03.md must be satisfied. Stop and ask if any action would violate SECURITY.md approval rules.
```

### Example 2) S07 Analysis screen — Claude Code (core screen)

**Files:** base set + `docs/screens/s07.md` + `docs/AI_PIPELINE.md` (s07_analysis_v1 schema) + `prompts/s07/v1.md` + `docs/data-model.md` (analysis_requests, expressions) + `docs/decisions/001-*`, `003-*`
**Reason:** This is an AI-output screen; prompt, schema, validation, and DB are all intertwined.

```
After reading the base session entry docs, implement the S07 analysis feature using:
docs/screens/s07.md, the s07_analysis_v1 schema and logging contract in docs/AI_PIPELINE.md,
prompts/s07/v1.md, the analysis_requests and expressions tables in docs/data-model.md, and ADR-001 and ADR-003.
Required: (1) validate output against the JSON schema and retry once on failure,
(2) log every LLM call to ai_request_logs including model_name and prompt_version,
(3) use Sonnet routing.
Write a plan in docs/exec-plans/ before implementing. When done, align prompt_version
with the front-matter in prompts/s07/v1.md so eval/s07-analysis/run_eval.py can detect regressions.
```

### Example 3) Prompt v1 → v2 improvement — Claude Code

**Files:** base set + `prompts/s07/v1.md` + `eval/s07-analysis/*` + `docs/quality-gates.md` + `docs/decisions/009-*`
**Reason:** Need objective eval score comparison to confirm the changed prompt is actually better.

```
Copy prompts/s07/v1.md to prompts/s07/v2.md and improve v2 to address weaknesses
likely to score low in eval/s07-analysis/test_cases.json (emotional nuance, tone match).
Then run `python eval/s07-analysis/run_eval.py --prompt-version v2 --baseline <previous run.json>`
and verify it meets the S07 criteria in docs/quality-gates.md (aggregate >= 4.0)
and the N=3 variance gate from ADR-009. If v2 scores lower than v1 or fails the regression gate, do not merge — report it.
```

### Example 5) New technical decision → ADR — Claude Code or Codex

**Files:** base set + `docs/decisions/INDEX.md` + relevant existing ADRs
**Reason:** Record the decision rationale so the same debate doesn't repeat later.

```
Read docs/decisions/INDEX.md and the relevant existing ADRs, then write a new ADR
for <decision topic> at docs/decisions/010-<slug>.md. Follow CLAUDE.md ADR rules strictly:
300-500 words, Drew DeVault / sourcehut style, rationale must be product or engineering logic only
(no portfolio or learning motivation), unverified numbers must say "estimated, pending verification",
no section symbol. When done, add a one-line summary to docs/decisions/INDEX.md.
```

### Example 6) Code review / merge — Codex (different agent from implementer)

**Files:** base set + relevant `docs/exec-plans/<plan>.md` + `docs/review-template.md` + `docs/quality-gates.md` + `docs/screens/<relevant>.md` + `SECURITY.md`
**Reason:** A different model must review to reduce blind spots; the change is "done" only after passing the 2-gate.

```
Review this PR using the docs/review-template.md format.
Gate 1 (spec compliance): does it satisfy the G-W-T in docs/screens/<relevant>.md and the docs/api/openapi.yaml contract?
Gate 2 (code quality): evaluate against docs/quality-gates.md criteria.
Check for SECURITY.md violations, state pass/fail explicitly, and record the result in docs/reviews/.
You must not be the agent that implemented this code (harness.md section 5). If uncertain, block the merge.
```

## 5. The one principle you don't need to memorize

When stuck, ask yourself:
1. **Don't know what to build** → [1] Blueprints (`docs/PRD.md`, `docs/screens/`, `docs/api/openapi.yaml`, `docs/data-model.md`)
2. **Don't know why it ended up this way** → [2] ADR (`docs/decisions/INDEX.md` first)
3. **Don't know if what was built is good** → [3] eval + quality-gates (`eval/s07-analysis/`, `docs/quality-gates.md`)
4. **Don't know how to work with AI** → [4] harness + templates (`docs/harness.md`, `docs/*-template.md`)

If you know which file to open for each of these 4 questions, you already know this project better than anyone.

**Verification principle:** For hard facts (APIs, pricing, security, model names) — official docs always win.
YouTube, blog posts, and AI answers are secondary; always cross-check against official documentation.

---

Prompt writing tips: (1) always have agents read the base set first → (2) explicitly name the target spec files → (3) embed the acceptance criteria (G-W-T or eval score) → (4) require a plan before implementation and a review after.
These 4 steps turn "vague instructions" into "correct results on the first attempt" — the core of ADR-004.
